# Custom note styles in Lectern

Researched October 13, 2026. This brief covers using a student's sample notes to guide the style of notes generated from a different lecture. It does not cover adding factual material from the sample to the new lecture.

This is feasible within Lectern's existing generation pipeline. After comparing the two proposals, I recommend having the user's selected agent derive a persistent personal style skill, retaining a few short example excerpts within it. Save a choice between **Default Lectern style** and **My notes style**, plus a choice for an individual generation. Keep the built-in style selected for existing users. The work includes a style-learning step, settings, local storage, prompts, and validation.

Google's [current prompting guidance](https://ai.google.dev/gemini-api/docs/prompting-strategies#zero-shot-vs-few-shot-prompts) describes using examples to guide formatting and phrasing. Anthropic's [prompting guidance](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#use-examples-effectively) also recommends relevant, structured examples for output format, tone, and structure. These support keeping examples alongside learned instructions. Neither establishes that an automatically generated style skill will outperform direct samples in Lectern. The recommendation below is an architectural judgment; style quality and cost still need measurement with real samples and the selected models.

Sending sample notes with every generation is the simplest implementation and preserves the exact examples. Its recurring input includes the chosen sample text, and each request must infer the user's preferences again. It is a reasonable first prototype or a useful baseline for testing.

Having an agent author a complete replacement for the current notes skill provides an inspectable, persistent artifact. However, the current skill includes factual grounding, coverage, Markdown requirements, and Hebrew display rules as well as style. Asking the agent to recreate all of those while learning a writing style adds unnecessary work. Reusing the same skill name also does not establish reliable replacement: [official OpenAI documentation](https://developers.openai.com/codex/skills/) says same-name Codex skills are not merged, and both can appear in selectors. OpenCode documents [its own discovery and loading behavior](https://opencode.ai/docs/skills/). Lectern should explicitly select the active instructions.

The recommended approach keeps a shipped **custom-note-styling** skill whose job is to derive a personal style from uploaded examples. Its output is a separate, instruction-only **lectern-personal-notes** skill containing concise style rules and representative excerpts. Lectern keeps its shared content and rendering requirements authoritative, and selects either the learned style or the built-in style for each job. The personal skill replaces the active style instructions in custom mode. The original bundled skill stays available for switching back.

Here, "learn" means extracting reusable instructions from examples. It does not mean changing model weights or relying on a persistent agent conversation. The agent authors the skill content; Lectern validates, stores, and supplies that content to future sessions.

The current implementation provides several useful starting points:

- [Prompts.swift](../Sources/Lectern/Generation/Prompts.swift) supplies the bundled notes contract inline for the general ACP path and has separate request and repair prompts for Antigravity.
- [GenerationService.swift](../Sources/Lectern/Generation/GenerationService.swift) handles both paths, normalizes the output, validates it, and attempts one repair when validation fails.
- [AntigravityACPClient.swift](../Sources/Lectern/Generation/AntigravityACPClient.swift) reads requested skill files and includes their complete instructions in the text sent over ACP. Its initializer already accepts `skillURLOverrides`, although the production `configured(for:)` factory currently uses no overrides. This is an existing extension point, not an implemented custom-style feature. Each Antigravity request uses a temporary workspace that is removed afterward, so persistent styles must live in Lectern's own storage.
- [ReferenceMaterialService.swift](../Sources/Lectern/ImportExport/ReferenceMaterialService.swift) already imports Markdown, text, Word/RTF, and PDFs with extractable text. Word extraction returns a plain string, and PDF extraction uses page text. These paths do not preserve all document formatting, and the PDF path does not perform OCR.
- [NotesContentView.swift](../Sources/Lectern/Views/NotesContentView.swift) already renders paragraphs, headings, lists, quotations, and tables. The app can therefore display more layouts than its generation contract permits.
- [ShiurAutomationService.swift](../Sources/Lectern/Automation/ShiurAutomationService.swift) calls `generateDirectly` for automatic notes. A preference applied only in the generation sheet would miss this path.

The main obstacle is the fixed style contract. The [notes skill](../.agents/skills/lectern-notes/SKILL.md) prescribes nested outlines, labels, wording conventions, and language-specific layouts. `NotesOutputValidator` also requires an outline, rejects sufficiently long flat lists, and rejects headings such as `Key Takeaways`. Custom mode must change which style rules apply throughout generation and repair.

I verified that obstacle with a temporary Swift diagnostic using the current validator, list scanner, and normalizer. A built-in nested outline passed. Paragraph notes failed the outline requirement, notes with a `Key Takeaways` heading failed the generic-heading rule, and a flat list of 12 concepts failed the nesting rule. The diagnostic did not change app files or invoke an AI provider.

The revised user flow is:

1. Add a **Notes** settings page. Show **Default Lectern style** and **My notes style** as the saved preference.
2. Let the student paste or import representative samples. Show the extracted text and allow editing. Start with pasted text, Markdown, and text files for predictable structure. Word and PDF support can reuse the importer once the preview makes formatting losses visible.
3. Provide **Create my style** using an installed, signed-in agent the student selects. Run the bundled `custom-note-styling` instructions with the examples and obtain a draft personal skill. This step runs when creating or updating the style, rather than before every lecture generation.
4. Show the inferred preferences and a preview. Let the student edit the preferences and choose **Use my style**. That action saves the skill revision and makes it the preference for subsequent manual and automatic notes.
5. In the generation sheet, show **Notes style** when Notes is enabled. Initialize it from the saved preference, with **Default Lectern style** always available. An individual choice should not silently change the saved preference. Switching back to the built-in style keeps the personal style available for later.
6. Relearn when the student changes samples or requests a style adjustment. Store the original samples and previous skill revision so a poor revision can be corrected or undone. Generated lecture notes should not become learning examples automatically.
7. If creation fails, preserve the previous usable style. If a selected style is missing or unreadable at generation time, use the built-in style and display the reason. Existing generated notes change only when the student regenerates them.

Use a small local style store for the first version, separate from lecture and course reference attachments. A proposed location is `~/Library/Application Support/Lectern/Note Styles/<style-id>/`. Store the original samples, an instruction-only `SKILL.md`, and metadata for the revision, sample fingerprint, creator agent/model, and active selection. Keep the saved mode in preferences. Lectern should save a completed revision atomically, then change the active pointer. This avoids requiring a new SwiftData model for a single global style. Multiple named styles and course-specific choices can follow later.

Resolve the choice once when a generation job starts, then pass an immutable style value through the generation service. Distinguish following the saved preference from explicitly selecting the built-in style. An absent override must not accidentally mean "use custom" when the student explicitly chose default. Snapshotting the skill revision prevents an edit in Settings from changing an in-progress job or its repair attempt. The creator agent and the later generation agent can be different because the saved artifact is text.

Separate the prompt rules into shared requirements and mode-specific style instructions. Shared requirements should preserve grounded lecture content, source boundaries, supported Markdown syntax, logical Hebrew character order, and existing Important/Test bookmark links. Built-in mode should retain the current outline instructions. Custom mode should use the sample for organization, heading patterns, phrasing, abbreviations, and list or paragraph choices. It should not copy the sample's subject matter, citations, or instructions into the new notes.

Have the creator produce style instructions and selected examples under a known output contract. Keep the generated artifact instruction-only, with no install commands, helper scripts, or global agent configuration changes. A structured response containing the skill body and a user-facing preference summary would let Lectern construct and validate the file itself. Validation establishes file shape and supported output features; it does not establish accurate style inference.

For Codex and OpenCode, compose the shared contract and selected style into `Prompts.notes`, as the current pipeline already supplies skill text inline. For Antigravity, extend the existing skill override mechanism or allow explicitly supplied instruction text so both creation and generation receive the selected contract. Supply the complete selected instructions again on its repair request. Keep the same style snapshot through both repair paths. Simply writing a new file into a provider's skill directory is insufficient for the current Lectern pipeline, which explicitly requests the bundled notes skill.

Package the creator skill with the app through `project.yml` during implementation, then run `xcodegen generate`. Store generated personal skills outside the app bundle and outside the user's global Codex/OpenCode skill directories. Keep shared requirements in the application-maintained contract so app updates can improve them without recreating every user's style.

Do not put style samples in ordinary `ReferenceAttachment` collections. Those collections are used as factual supporting context and are also supplied to other generation tasks. Personal style examples should be supplied only to notes generation. Explain in the sample editor that using a sample sends its text to the selected AI provider, as lecture generation already does.

Make validation aware of the selected mode. Keep the current checks for built-in mode. In custom mode, retain checks for empty output, accidental whole-document wrappers, and required bookmark links, while allowing supported paragraph layouts, flat lists, and the student's section conventions. Review the length and Hebrew-script heuristics as well, because they currently assume the built-in style. Format validation does not establish factual accuracy or complete lecture coverage.

For the first release, promise matching writing style and organization within Lectern's Markdown presentation. Exact Word/PDF page appearance is a separate feature. Tables render in the app, but the current Google Docs converter handles them as body text rather than creating native tables, so table-heavy styles need export work or a documented restriction before being promised.

The saved skill still consumes input tokens whenever its instructions are read or injected. In Lectern's current pipeline the complete skill text is injected, so native skills' progressive disclosure does not automatically reduce the notes request. Recurring input can be smaller if the learned rules plus excerpts are shorter than the full samples. Creation adds a separate input/output cost, so savings depend on sample length and how many generations reuse the style. No specific savings percentage or latency improvement has been measured.

The implementation would touch the generation sheet, settings, generation service, prompt builders, notes skill, a new creator skill/service, and a new style store. Add focused checks for preference persistence, explicit default overriding a saved custom choice, missing or invalid skills, failed creation, concurrent jobs, automatic generation, revisions, and both repair paths. Preserve the existing default notes regressions.

Before choosing the final prompt design, compare three approaches on the same transcripts and sample sets: direct samples, generated rules alone, and generated rules plus short examples. Use representative paragraph, numbered-outline, and mixed English-Hebrew styles, with subjects different from the samples. Evaluate user-rated style fidelity, lecture coverage, factual accuracy, content copied from samples, rendering/export behavior, token usage, and repair frequency. Test the installed providers the product intends to support. That experiment is still outstanding.

No app behavior changed during this research. The knowledge graph guided navigation, and current source supplied the final evidence where graph metadata was out of date. Follow-up graph coverage was current for the relevant provider and prompt files. Existing tests also confirm that the bundled notes instructions are sent inline to Codex/OpenCode and through ACP text to Antigravity; they were read, not rerun during this comparison. No custom skills were installed and no live model generations were run. Provider consistency, style fidelity, and the prompt cost remain to be measured during implementation.
